## I did not apply the union as given — I replaced it with rules

You were right that the union is needed and right that the regex list is a
treadmill. So the closed-world half is now seven rules about *permitted usage*:

| | rule |
|---|---|
| R1 | `unsafeHTML(renderMarkdown(` is present |
| R2 | each identifier imported **unaliased** from the one module allowed to provide it, value import not `import type` |
| R3 | neither identifier re-bound by a local `const`/`let`/`var`/`function`/`class` |
| R4 | outside its import statement, neither identifier may appear in **any** position other than immediately called — `name(` |
| R5 | every `unsafeHTML(…)` argument **is** a `renderMarkdown(…)` call and nothing else |
| R6 | every relative import specifier resolves into the scanned set; every dynamic import specifier is a plain quoted literal |
| R7 | no unicode/hex escape in code |

R4 is what makes this not round 5's problem: `const raw = unsafeHTML`,
`{ raw: unsafeHTML }`, `const { unsafeHTML: raw } = await import(…)`,
`unsafeHTML as unknown as F`, `export { unsafeHTML }`, and a *parameter* named
`renderMarkdown` are all one violation, and none had to be foreseen.

## Residue, stated plainly

Because "not scanned" is indistinguishable from "clean" in the results:

- `(0, eval)('unsafeHTML')`, `globalThis[k]`, `new Function(…)` are invisible to
  every rule here. Nothing short of a binding resolver catches these — which is
  your typescript-eslint / Trusted Types item, and it remains the real answer.
- Non-relative specifiers are not resolved. There are no `tsconfig` `paths` and
  no package `imports` field today (I checked), so a bare specifier is a
  `node_modules` package. If either is ever added, R6 has a hole.
- Template literals are deliberately not stripped — the sinks live inside `html`
  templates — so no rule may assume their contents are inert.
