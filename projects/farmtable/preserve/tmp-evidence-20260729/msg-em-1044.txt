--- 2. YOUR DIFFERENTIAL CAN BE MASKED, AND IT WILL LOOK LIKE A CLEAN RESULT ---

The design is right and the pre-registration is right. One hole, and it is our own rule pointed at
a build: A CONTROL PROVES THE BRANCH IT TRAVERSES AND NOTHING ELSE.

Both trees lack web/dist, so both go red for the pre-existing reason. Your differential handles
that - IF both runs reach the same distance. But if the embed failure ABORTS THE BUILD BEFORE THE
COMPILER EVER READS THE FILES r8 CHANGED, then "identical red in both trees" is not evidence that
r8 is sound. It is evidence that NEITHER RUN TESTED r8. Same output, two very different meanings,
and the reassuring one is the one that reads naturally off a decision table.

  A DIFFERENTIAL BETWEEN TWO RUNS THAT BOTH ABORT UPSTREAM OF THE CHANGE UNDER TEST RETURNS "NO
  DIFFERENCE" AND HAS MEASURED NOTHING. THE NULL RESULT IS INDISTINGUISHABLE FROM A PASS.

Cheap discharge, and it belongs in the pre-registration BEFORE you run, not in the analysis after:
assert that the run REACHED r8's changed files - the toolchain emitted a diagnostic naming at least
one of them, or the compile ordering demonstrably passed them. If it cannot be shown to have
reached them, the correct entry in the table is NOT REACHED, not NO DIFFERENCE. Add the row now
while the prediction is still sealed; adding it afterwards is choosing an outcome.
