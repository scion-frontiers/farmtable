# Findings

## F1 — CRITICAL. `consumeFixtureTable` pins *delivery*, not *consumption*. One line defeats it.

The generator proves the loop was **handed** every entry and **yielded** every entry. It cannot
observe whether the loop *body* did anything. A `continue` as the body's first statement leaves
all 27 entries yielded, the name recorded, the census satisfied, and every fixture unexercised.

```
# cell N-1
web/src/util/markdown.test.ts:5065, insert as first statement of the loop body:
      if (label) continue;
```

**Expected (author's model):** RED. **Actual:** `GREEN — markdown sanitizer: 83 checks passed
(131 assertions)`, `tsc --noEmit` 0. Twenty-seven sink-binding evasions unexercised, no signal.
Reproduced independently at a second site (`N-1b`, `ARITY_EVASIONS` :745) — also GREEN.

This is strictly cheaper than the defect being fixed: `.slice(0, 0)` is a one-site edit that now
goes RED; `continue` is a one-site edit that stays GREEN. **Root cause:** the round asserted a
property of the *iterable* when the property that matters is of the *loop body's effect*. The six
loops all accumulate into a `survived`/`missed` array and assert `length === 0` — an assertion
that only ever *permits* an empty result, which is exactly rule 22′'s definition of vacuous. The
wrap did not change that; it only guaranteed the array was iterated.

**Shape of the fix (not implemented — this is the developer's call):** the loops need a *positive*
outcome, e.g. a per-loop count of fixtures actually evaluated, asserted against the same expected
count the generator already knows. `HANDLER_BEARING` and `COUNT_PIN_DELTAS` already do exactly
this and are the only two fixture loops in the file that survive their own neutering (§4).

# 2 · The docblock refutation — verified, and what pins the census

**Independently confirmed** (`/tmp/r10lab/gen.mjs`, standalone Node, no test harness):
```
after break      -> threw: false | trailing arm reached: false | name recorded: false
after full drain -> trailing arm reached: true  | name recorded: true
```
The author is right: `break` invokes the generator's `return()`, the trailing arm is unreachable
from a break, and the **census** is what catches an abandoned loop. The corrected docblock is
accurate.

**I then ran the mirror the author did not**, and it is the more interesting half:

- `T-3r` (author's T-3 — disarm the **length** arm, keep the trailing arm) → **GREEN**, reproduced.
- `T-4` (disarm the **trailing** arm, keep the length arm) → **GREEN**.

So the two arms are *mutually* redundant. But they are not symmetric: `yielded` counts exactly
`table.length`, and the length arm has already established `table.length === expected`, so **the
trailing arm is provably unreachable whenever the length arm is live** — it is dead code today,
not defence in depth. Nothing in the self-test exercises it in either direction (its four `drain`
cases all hit the length arm; the abandoned case hits the census). The docblock says the trailing
arm "is kept because it is reachable from a `throw` inside the loop body caught upstream"; no
wrapped loop has such a `throw`, so that reachability is hypothetical.

**What pins the census: nothing, and that is not an acceptable terminal position — it is F3.**
The report frames it as "the same terminal position the check total has always occupied". That
framing would hold if no cheaper option existed, but the sibling census three hundred lines away
*is* pinned, by one line, and adding the same line is measured GREEN-clean (`FIX-1c`). A terminal
position that a sibling has already escaped is an omission, not a limit.

# 7 · Deliverable 4 — is a file-count pin evidence of non-vacuity? **No. Measured.**

The brief asked for a ruling because two of the author's six emptied-table REDs
(`INERT_EXTENSIONS` 53≠51, `EXTRA_SCANNED_FILES` 50≠51) are file-count pins. I reproduced all six
(§8) and then tested the pin itself rather than reasoning about it.

- **K-1 — count-neutral corruption.** Replace 8 of `INERT_EXTENSIONS`' 14 entries
  (`.png .jpg .jpeg .gif .ico .webp .woff .woff2`) with `.zz1`–`.zz8`. Table length unchanged at
  14; no `src/` file carries those extensions, so the corpus stays 51. → **GREEN, 83/131.**
- **K-2 — positive control.** Change one *count-moving* entry (`.css` → `.zz0`), same length 14.
  → **RED**, 8 checks, "found 52".

**Ruling.** A file-count pin establishes non-vacuity of the **enumeration**, not of the **table**.
Under rule 22′ it demands a positive outcome (51 files) from the file walk, which the table merely
feeds. Its discriminating power over `INERT_EXTENSIONS` is exactly **6 of 14 entries** — the six
that occur in `src/`. The other 8 are, measurably, decoration: they can be replaced with garbage
and nothing fires. So the RED in the author's table is **form (5), a post-hoc tally**, with
respect to the claim it is offered for.

This does not make the author's conclusion wrong — the tables are non-vacuous — but for
`INERT_EXTENSIONS` and `EXTRA_SCANNED_FILES` the evidence offered does not establish it, and this
project has accepted count pins as evidence for several rounds. **Recommendation:** stop counting
a count-pin RED as non-vacuity evidence unless a count-neutral corruption is also shown RED.
