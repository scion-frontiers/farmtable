## MUST 1 + 2 — C-1 and the two property pins

**Fixed by deriving, not mirroring**, the route the brief marked strongly
preferred. `RestrictLabelWriteToSnapshot` now computes
`after := applyLabelDelta(snapshot, add, remove)` and emits the minimal
`(add, remove)` carrying `snapshot -> after`. The oracle **is** `applyLabelDelta`,
so the restrictor cannot drift from the gate it narrows: there is no second copy
of the rule to disagree with.

The docblock's old claim — "It is exactly the complement of applyLabelDelta …
The two must agree" — was the false guarantee that let C-1 through, and is gone.

Two things found while designing it, neither in the brief:

- **Removals are now emitted in the snapshot's spelling, not the caller's.**
  This closes F-2 as a side effect. `labelNameToID` looks up
  `s.labelIndex[strings.ToLower(name)]` and the index is built with
  `strings.ToLower(l.Name)` and **no `TrimSpace`**, so a padded caller spelling
  resolves to nothing and the removal silently evaporates. Emitting the
  snapshot's spelling is the only form guaranteed resolvable.
- **A hazard, guarded.** If `ent.Task.Labels` ever carries two entries sharing a
  match key, `applyLabelDelta`'s dedup drops one, and a naive derivation would
  emit a removal the caller never asked for. The `removeKeys[key]` safety belt
  prevents that; it is documented in the code and covered by a named row.

## SHOULD 5 — `req.Type` unvalidated

Two halves, deliberately fixed in two different layers.

**Destructive half, in the store.** `TypeLabelSwap` returns `(nil, nil)` when the
new type maps to no label and the type is non-empty. `TypeToLabel` had nothing
to add for an unrepresentable type, but the remove loop ran anyway, so any
garbage string deleted the issue's real type label. `""` still means "clear the
type" and still clears.

**Shape half, at the RPC boundary.** New `validateTaskType` rejects
blank-but-not-empty and >128 runes.

**I did not implement the audit's suggested allow-list, on purpose.** There is no
set of valid types the server can know: the Ent schema declares
`field.String("type").Optional().Default("")` so native collections can use
arbitrary types, and on a GitHub collection the valid set is the operator's
`github.labels.types`, which the server does not hold. An allow-list would break
every native caller and put the server in the business of knowing a
per-collection platform config. The reasoning is recorded in the doc comment.

| mutant | exit | RED |

| M5b blank-type check neutered | 1 | 6 rows |
| M5c length bound neutered | 1 | 3 rows |

| M5e InsertTasksAfter call site dropped | 1 | 3 rows |

**The pin caught a defect in my own change while it was being written.** The

was RED on `create/*` and `insert_after/*` and green after moving the call. This
is the entire argument for the RED-first rule.

## SHOULD 6 — cross-table config key collision

New `checkLifecycleKeyCollisions` rejects any `priorities` or `types` key that
normalises onto a label this deployment writes for one of its own stages.

**The oracle is the functions themselves**: the label side is `StageToLabel`, the
normalisation is `stripForMatch` — the identical expressions `PriorityLabelSwap`
and `TypeLabelSwap` use to decide a label is theirs to remove.

**MERGE GATE satisfied.** The brief required this to ship with M-1. M-1 is in this
branch's history at `0570824`, stated in the commit message and in the test file.

| mutant | exit | RED |
|---|---|---|
| M6a check removed entirely (= round-7 state) | 1 | 9 |
| M6b terminal stages only | 1 | 1 row (`non-terminal stage`) |
| M6c oracle reimplemented with a hardcoded prefix | 0 | **SURVIVOR — see below** |
| M6d config key not normalised | 1 | 2 rows |
| M6e **over-reach**: stages table checked too | 1 | 1 row *(after `f1e4705`; survived before)* |

### Two survivors, both real, both addressed

**M6e survived the first version.** My stage-alias control rows used keys
`"doing"` and `"shipped"`, which do not normalise onto any stage — so they never
exercised the exemption they were written to protect. Added a row whose keys *are*
stage names (`{completed: completed, duplicate: wont_fix}`), both legitimate
configs that load today. M6e is now RED.

**M6c survives and cannot be killed.** Replacing the `StageToLabel`/`stripForMatch`
oracle with a hardcoded `"ft:stage/"` literal passes every test, *including* the
custom-push-prefix row — that row only pins the error message, which calls
`StageToLabel` separately. The two forms are equivalent by construction:
`StageToLabel` writes `pushPrefix + "stage/" + stage` and `stripForMatch` strips
exactly those, so the round trip is the bare stage name for every prefix and no
config separates them.

I am reporting this as an equivalent mutant rather than a killed row. The
oracle-is-F choice here is **structural, not measured** — it stays correct if
either function's spelling changes. What I could do is pin the equivalence
itself, so the day it stops holding is a test failure rather than a silent
divergence: `TestLifecycleKeyCollision_OracleIsStructurallyEquivalentToday`. The
code comment now says the choice is structural rather than claiming a
measurement I do not have.

# Where this brief was wrong

Required deliverable. Four items.

### 1. Item 3's list of `stageWriteAllowed` call sites is wrong twice

The brief says the flag should be set "only by the stage arm, `ClaimTask` and
`CloseTask`".

- **`CloseTask` does not route through `writeLabelSwap` at all.** It kept its own
  inline best-effort swap that swallows errors on purpose. The brief's *own item
  4* states this, so item 3 contradicts item 4.
- **It omits `UpdateTask`'s caller-supplied `add_labels`/`remove_labels` arms**,
  which *are* priced — by the server's label-delta gate at `server.go:795-812` —
  and then narrowed against the authorized snapshot. Setting them
  `stageWriteForbidden` as written breaks **10 server tests** plus my own
  positive control (mutant M-P2).

Shipped with six call sites: stage arm, `ClaimTask`, both caller-supplied label
arms → `stageWriteAllowed`; priority and type arms → `stageWriteForbidden`.

### 2. Item 8's "vacuous — it cannot fail" is false as stated

The round-7 test catches the F7 defect it was written for. Measured both ways
against the real file from `1d4442f`, table above. The true gap is that it could
not distinguish a declined deletion from no write at all. Had I acted on the
brief's wording — "a test that cannot fail is worse than no test" — and deleted
it, real coverage would have gone with it.

### 3. Item 5's implied fix is not safely implementable as written

The audit recommended rejecting unknown types at the RPC boundary. There is no
allow-list the server can hold: the Ent schema declares type as an open string
for native collections, and the valid set on a GitHub collection is operator
config. Implemented as shape-only validation, with the destructive half fixed in
the store where the knowledge actually lives.

### 4. Item 6's premise is right but its scope needs a caveat the brief omits

"Reject any types/priorities key that normalises onto a lifecycle stage" is
correct. What the brief does not say is that the neighbouring generalisation —
also checking the `stages` table — is an over-reach that rejects configs which
load today (`{completed: completed}`, `{duplicate: wont_fix}`). I found this only
because a mutant testing that generalisation survived my controls. Anyone
implementing item 6 from the brief alone is one plausible refactor away from
breaking working deployments.
