### 3.3 F1 — `unionStages` order preservation is load-bearing for PRICE, and the comment says it is cosmetic

This follows directly from 3.2 and is a **new finding, `[OPEN]`** (it came out of O3/O9).

`unionStages`' docstring justifies order preservation solely as presentation:

> *"Order is preserved rather than sorted because these sets are rendered into
> authorization error messages, and a set whose order depends on map iteration produces
> a different message on every run."*

That is true and incomplete. Because `SameStageSet` compares sequences, the *order* of
`unionStages`' output decides whether the two endpoints compare equal and therefore whether
the write is priced at all. The `LabelDeltaLifecycleStages` monotonicity argument is written
entirely in set language ("the price is the set of scopes over the cross product",
"`writePrice ⊇ readPrice`") over a primitive that is not a set comparison.

**Measured — M1, sort `unionStages`' output** (the exact refactor the cosmetic justification
invites, since sorting *improves* message determinism):

```
mutation: append sort.Slice(out, ...) to unionStages
go test -run TestLabelWritePrice_IsMonotoneInThePredicate  ->  EXIT 1
"WRITE PRICE IS CHEAPER THAN THE READ PRICE" cells: 48
```

**48 cells get cheaper.** So the property test *does* pin this — a genuine strength, and it
is the strongest non-vacuity evidence I obtained for the property test. But a maintainer
reading the docstring is told the only cost of sorting is message churn, when the real cost
is 48 silently cheaper authorization decisions. Severity: **Suggested** (documentation), not
Required, precisely because the pin holds.

**UNVERIFIED, AND I AM FLAGGING IT AS SUCH:** I did not get to read *why*
