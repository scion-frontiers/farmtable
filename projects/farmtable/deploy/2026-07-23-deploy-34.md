### Check (e): Backward Compatibility — Token-Based Consumers

The deployed server uses `NewStoreTokenLookup` (store-backed token resolution), not
the deprecated `LegacyTokenAuth`. Existing `ft_` tokens:

1. Are accepted through the same extraction path (`x-farmtable-token` header first,
   then `Authorization: Bearer` fallback)
2. Resolve to real user IDs via the database token store (not `uuid.Nil`)
3. Pass `RequireIdentity()` checks on mutating RPCs

Evidence: Checks a1/a2 proved that the existing `ft_` token resolves to user
`a948da6d-10cb-4d5c-8167-b1a35de52946` and supports both read and mutating RPCs.
The decomposer binary and `ft` CLI both use the same dual-header pattern
(`authorization: Bearer` + `x-farmtable-token`) and will continue to work.

The only caveat: IAP OIDC token injection is still required to reach the service
(this was always the case). The `ft` CLI and decomposer don't have built-in IAP
injection — callers must provide the IAP identity token separately.

`LegacyTokenAuth` is deprecated and returns `uuid.Nil`, which would fail
`RequireIdentity()` on mutating RPCs. However, it is **not** used in the deployed
server — the server uses `NewStoreTokenLookup` when `FARMTABLE_TOKEN` is set.

- **Result: ✅ PASS** — Existing `ft_` tokens work through the new auth model.
