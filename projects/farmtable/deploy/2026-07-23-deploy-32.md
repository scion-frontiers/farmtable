Key changes in this deploy:
- **Feature 59: x-farmtable-token IAP Auth Header** (PR #136):
  Adds `x-farmtable-token` gRPC metadata fallback header so the `ft` CLI /
  decomposer can authenticate against the Cloud Run service when it's behind IAP.
  IAP consumes the `Authorization: Bearer` header for its own OIDC token,
  colliding with Farmtable's own use of that header for its app-level `ft_...`
  token. The server-side `extractToken()` now checks `x-farmtable-token` first,
  and all clients (CLI, decomposer, web) send the token via both headers.

**Analysis:** Request passes IAP (valid OIDC token). Server receives IAP's JWT

expected behavior — the connection works but the user is not authenticated at

### TEST 3: ft_ token in Authorization ONLY (old-style, no IAP bypass) — PASS (negative test)

Sent: `authorization: Bearer <ft_token>` only (the OLD authentication approach).

```
Result: BLOCKED by IAP as expected — rpc error: code = Unauthenticated
  desc = Invalid IAP credentials: Unable to parse JWT
```

**Analysis:** IAP rejects the `ft_...` token because it's not a valid OIDC JWT.
The request never reaches the backend. This proves that the old `Authorization:
Bearer <ft_token>` approach is broken when IAP is active, confirming that
`x-farmtable-token` is NECESSARY (not redundant) for IAP-protected deployments.

### TEST 4: x-farmtable-token ONLY (no Authorization header) — PASS (negative test)

Sent: `x-farmtable-token: <ft_token>` only (no Authorization header at all).

```
Result: BLOCKED by IAP as expected — rpc error: code = Unauthenticated
  desc = Invalid IAP credentials: empty token
```

**Analysis:** IAP blocks because there's no valid OIDC token. Even though the
`x-farmtable-token` is correct, IAP must be satisfied first. This confirms that
both headers are needed: IAP OIDC token in Authorization + farmtable token in
x-farmtable-token.

### ft CLI Direct Test (Expected Failure)

Attempted to use the `ft` CLI binary directly against the Cloud Run URL:

```bash

  /tmp/ft-deploy-32 collection list
```

```
Error: Invalid IAP credentials: Unable to parse JWT
```

**Analysis:** Expected failure. The `ft` CLI's `authCtx()` sends the same
farmtable token in BOTH `authorization` and `x-farmtable-token`. IAP rejects
the `ft_` token in `Authorization` before the request reaches the backend.
To use the `ft` CLI through IAP, a future update would need to send a proper
IAP OIDC identity token in `Authorization` while keeping the farmtable token in
`x-farmtable-token`. Alternatively, `gcloud run services proxy` can be used for
local development to handle IAP auth transparently.
