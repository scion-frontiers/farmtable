# MUST — these four block the round

## 1. C-1, CRITICAL — cross-list label-write authorization bypass

`[MEASURED-BY-review-194-r7, independently reproduced by me from source, and independently
reproduced again by audit-194-r7]`

`UpdateTask{add_labels:["ft:stage/completed"], remove_labels:["ft:stage/completed"]}` on a
GitHub task that does NOT carry the label, caller holding only `task:write`:
- `applyLabelDelta` — **remove wins**: it builds the `removed` set from the remove list first
  and skips those keys, so `before == after`, `SameStageSet` sees no change, **nothing is
  charged**.
- `RestrictLabelWriteToSnapshot` filters the add list and the remove list in **two
  independent loops with no cross-list test**, so the add survives and the remove is dropped.
- The write applies the label. Task becomes terminal and unclaimable. Reversal costs
  `task:accept`. Retryable, free.

`[MEASURED BY ME]` This is a **regression introduced by round 7**. At base `6ced24e` both
lists passed through verbatim and passthrough applied adds then removes, so the identical
request netted to nothing.

**Fix (audit tested it, 8 attempts, 0 residual):** before the present/absent test, drop from
`add` any entry whose `labelMatchKey` also appears in `remove`.

> **LOAD-BEARING: the cross-list test MUST use `labelMatchKey`, NOT `==`.** With string
> equality, case-split (`add:"ft:stage/completed"` / `remove:"FT:STAGE/COMPLETED"`) and
> pad-split both bypass it. `[MEASURED-BY-audit-194-r7]` Put a comment at that line saying
> why, because it is exactly the spot someone "simplifies" into a live vulnerability.

**Strongly preferred alternative if you have the budget — derive, don't mirror.** The root
cause is that the restrictor reimplements `applyLabelDelta` by hand, so the two can always
drift; C-1 *is* that drift, and the docblock asserting they agree is what made it invisible.
Instead: compute `after := applyLabelDelta(snapshot, add, remove)`, then emit the minimal
`(add, remove)` that carries `snapshot -> after`. **Agreement then holds by construction and
no future change to `applyLabelDelta` can desynchronise them.** If you take this route, say
so prominently and the property tests below become regression pins rather than the guarantee.

## 2. The pins for C-1 — SHIP BOTH P1 AND P2, NEVER P1 ALONE

`[MEASURED-BY-audit-194-r7 against the real HEAD implementation]`

- **P1**: `applyLabelDelta(snap, Restrict(snap, add, remove)) == applyLabelDelta(snap, add, remove)`.
  Measured `P1=false` on C-1 and `P1=false` on a case-blind mutant. It has real content.
  **Its blind spot is structural, not a missing input:** P1 quantifies over outcomes *against
  the snapshot only*, so it cannot catch a narrowing failure that is a no-op against the
  snapshot but not against drifted remote state — the A-4 class. No extra test case closes
  that; the quantifier itself is snapshot-relative. *P1 misses the bug the function was
  written for and catches the regression introduced while fixing it.*
- **P2 (minimality)**: no returned entry may be a no-op against the snapshot.
  `add`: reject if `k == "" || present[k] || removeKeys[k]`. `remove`: reject if `k == "" || !present[k]`.
  Measured: P2 rejects the pre-fix implementation on A-4-original, A-4-re-add **and** C-1,
  with no false positive on a legitimate priced edit.

P1 covers over-/mis-narrowing, P2 covers under-narrowing. **Together they cover all four
known defect shapes; neither alone does.**

**Both pins must be demonstrated RED before you call them done.** Run each against the
pre-fix implementation and record the output. A pin nobody has seen fail is not a pin — this
project has produced fourteen harnesses that printed a confident wrong number.

`[MEASURED-BY-audit-194-r7, Addendum 1 §4, where it explicitly revised its own earlier
