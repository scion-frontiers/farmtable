## Scope

Two defect classes, and it is worth naming them separately because the round
kept confusing them.

**Class one: comments that state a reason which is not true** (B1, B2, B9, B10).
These are not cosmetic. B1's comment claimed no input path to a collection's
`remote_data` could carry a structpb-hostile Go type — a claim about *types* —
and cited `entstore.go:408` and `:898` as evidence. A review leg falsified the
claim by passing a `map[string]string` into `CreateCollection`. Worse, both
cited line numbers **resolve**, to plausible-looking `SetRemoteData` calls that
are on the *task* path, not the collection path. A reader who responsibly went
and checked came back with false confidence. A wrong citation that resolves is
more dangerous than a missing one.

**Class two: instruments that cannot fail** (B3, B4, B5, B6, B7, B8, B11). Tests
that were green for reasons unrelated to what they claimed to measure.

## What was established, and what was not

**Established by measurement.** The `remote_data` drop was silent *and* its log
line was untested while appearing tested: deleting the `log.Printf` outright left
the suite green, and that mutant survived r5. The mechanism is worth keeping —
another test *causes the line to print*, so a human running with `-v` sees it
and nothing asserts it. Output a person observes while reading a test run is not
coverage, and it is the most convincing kind of non-coverage there is.

**Established by measurement.** The web dashboard *does* consume collection
`remote_data`, in two places, as a write-authorization gate — `capabilities.ts
getCapabilities` and `ft-app.ts isCollectionWritable`. Three prior review legs
searched for places the dashboard *renders* `remote_data`, found none, and were
all correct. The dashboard never prints, interpolates or binds it. **It branches
on it.** A rendering-keyed search is structurally incapable of finding a
capability sink, and this is the round's transferable lesson: the failure was
one of method, not of leg reliability.

**The mechanism behind the earlier rounds' misses, corrected.** The working
theory during this round — mine, asserted confidently, and wrong — was that a
rendering-keyed search is *structurally incapable* of finding a branched-on
consumer. The instrument read measured otherwise: such a search found the
consumer **eleven times, from round one.** The actual mechanism is narrower and
cheaper to check:

> A negative's conclusion was written at a wider scope than its own evidence,
> inside the same document. The consumer is present in the report's evidence and
> absent from its conclusion.

Every negative in this round was re-read against that one question — does the
scope of the conclusion match the scope of the evidence actually gathered? — and
narrowed where it did not. **Four narrowed** (B1, B4, B5, B9), four confirmed
sound (B2, B3, B6, B8/B10). **B11 was not exempt and did not pass**; see the
hole recorded below.

The two most consequential narrowings: B1 concluded that *no in-tree caller*
populates the collection params from evidence covering **three named call
sites**, without establishing that the enumeration was exhaustive — the same
shape as the failure it was fixing. B4 concluded the scanner was no longer blind
from evidence covering **four shapes the author thought of**, which are the
shapes least likely to be the blind spot that matters.

The useful contrast is B3, whose negative is sound: it asserts zero log output
from a call it made itself, under a pinned clock, with the buffer captured.
**Bounded to an event it caused, not generalised to a tree it searched.** That
is what a defensible negative looks like.

**Not established.** Anything requiring a wide build. No `go build ./...`,
`go vet ./...`, `go test ./...`, `npm test` or `make` was run; the project build
token was never spent. Compilation of the three touched packages follows from
their targeted runs passing. Compilation of untouched packages is unverified,
and a single `go test ./...` is recommended before merge.

## The fail-closed accident was left armed

The sanitizer is type-preserving, so unrepresentable Go types (`[]string` for
`labels`, `[]map[string]any` for `sub_issues`) reach `structpb`, which refuses
the whole struct and yields a nil field. This is an accident, not a design, and
it is currently the thing preventing passthrough `remote_data` from flowing.

The standing hazard is that normalising `[]string` to `[]any` in the sanitizer
looks like an obvious tidy-up and would **switch passthrough `remote_data` on
for the first time.** It was not done. The one place the temptation was live was
B5's new route-level fixture, where a `[]string` would have made the test pass —
for the fail-closed reason rather than the routing reason. It uses `[]any`, so
the route test measures routing and the accident stays measured where it is
measured. No expected value was edited to make a test pass.

## Net scanner count went down

The standing ruling was: do not add a sixth hand-written scanner. Honoured in
both directions. B4 **removed** a hand-rolled Go lexer (`maskGoLiterals`,
`firstTopLevelSeparator`, a regex enclosing-function matcher) in favour of
`go/ast`, and its fixture table became 21 compilable snippets so the parser
checks the fixture instead of the author's eye. B11 declined to hand-roll a
TypeScript one.

B11 is an **occurrence census**, not a parser: two fixed identifiers, counted
everywhere in `web/`, including comments, strings and generated code. It
deliberately **over-approximates**. All five prior scanners failed by trying to
understand structure and getting it silently wrong; a census has no shape it can
fail to recognise, so its errors are all in the noisy direction and noisy fails
closed. It is an allowlist of eight individually-named sites with exact
multiplicities — **not** a permitted category such as "web may read collection
`remote_data`", because a category grants the next consumer for free, which is
how this one went five rounds unnoticed.

### The guard has a known, measured, unfixed hole

Recorded here rather than only in the scratch report, because a known hole that
lives outside the repository is invisible to the next person who touches this.

**A dynamically-accessed read, added to a web file that currently mentions the
field nowhere, is invisible to the census and the guard stays green.** Measured:
planting a four-line `canWrite` using `(collection as any)['remote' + 'Data']`
in `ft-collection-list.ts` produced no failure, and a grep for both identifiers
on the mutated file returns zero. No mention is added and none removed, so both
of the guard's directions are silent by construction.

This is a live capability consumer doing the same job as the two declared ones.
The guard catches literal additions and substitutions; **it does not catch a
determined evader, and its own limits block explains how to walk past it.** The
plausible remedies are a TypeScript parse — which the no-sixth-scanner ruling
exists to prevent — or checking where the value is *received* rather than where
it is *named*. Neither is designed and neither is claimed to work.

The prose around this was also wrong, and the correction matters more than the
hole. The commit message and report claimed the stale-direction assertion was
"the only thing standing between this guard and the evasion someone would
actually reach for." The evidence for that was a **substitution** mutant; the
claim was about dynamic access **as a class**. Against pure **addition** the
stale check is inert. Documented limit, overstated mitigation, sitting in the
same file.

### Its positive control

Planted a **serialisation** sink
(`JSON.stringify(collection.remoteData)`) — a consumption class nobody had
enumerated — and the guard caught it. A control that plants a class you already
thought of only proves the guard implements your taxonomy. The second control
replaced a declared read with dynamic access `(collection as any)['remote'+'Data']`;
that line contains neither identifier and is invisible to the census *as a
mention*, but it is caught as a **disappearance**. The stale-direction assertion
is the only thing standing between this guard and the evasion someone would
actually reach for.

## A defect this round reproduced while fixing it

Commit `7cee4a6` shipped a comment claiming the new guard's runner is "invoked by
every build, every CI job and every developer reflex in this project." Two
thirds false: there are **no CI jobs** (`.github` holds only issue and PR
templates; no workflows directory) and **the image builds do not run it**
(`Dockerfile` and `Dockerfile.server` each `RUN npm test`; neither runs

That is class one, written fresh, in the same round convened to remove it, in
the confident register that makes such prose survive review. Corrected in
`2f62f63` as a **separate commit rather than an amend** — the amend would have
hidden the only evidence in this branch that the defect class is not somebody
else's. A neighbouring claim that went unmeasured was dropped rather than
restated.

## What actually executes the new guard

`go test ./...`, which is `make test-go`, which is half of `make test`. That set
is real and complete, and it is not universal.

There is no location in this repository that is universally executed, and this
is a genuine trade rather than a win. A guard in `web/` is enforced by both
image builds and invisible to a Go-only workflow — CLAUDE.md warns about exactly
that, telling agents not to substitute a bare `go test ./...` because the
URL-scheme guards in `web/src/util` are executed only by `npm test`. A guard in
Go is the mirror image. This one is in Go because the person it needs to stop is
a Go developer changing `remote_data`'s server-side shape, and `go test ./...`
is that person's reflex. If image-build enforcement is wanted, the answer is a
second copy in `web/`, not a move.

## Method notes for the next leg

- **A green from a rewritten instrument proves nothing.** B4's rewrite was
  validated with paired mutants (one red, one green-only-after) rather than by
  argument. Every "now caught" row carries per-row execution evidence; a row
  without it is unresolved, not resolved.
- **A positive control must have a positive outcome.** Several tests here would
  have passed for any reason at all — including the field being empty — without
  a control that flips the property. B8's 2×2 includes a both-carriers-deleted
  row that must become representable.
- **An instrument error is a finding, not an embarrassment to tidy away.** The
  first probe for B7's end-to-end evidence used `panic`, which tore down the
  test binary so all eight rows died together and destroyed the differential it
  was measuring. Replaced with a counting write to stderr, and recorded at the
  point it happened.
- **The shell is zsh.** `grep --include=*.go` unquoted is a fatal expansion
  error, and it presents as an empty result — a false negative arriving through
  the shell rather than through an instrument, which is the same shape as the
  bug class this round is about.
