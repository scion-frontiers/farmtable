## C-1 — attacked directly, and it held

The claim that GitHub passthrough values carry non-structpb-representable Go types, making the
representability check a real guard, is **TRUE and instrumented**.

- `issueLabels` is `make([]string, len(...))` — non-nil even for an unlabelled issue — and
  `issueBuildRemoteData` sets `"labels"` in the map literal, not under a conditional. So every
  passthrough `remote_data` contains a `[]string`, which `structpb.NewValue` has no case for.
- I expected to report that the pin only tests the protobuf library (no test anywhere calls
  `issueBuildRemoteData` or `issueLabels`; the AST scanner reads `kv.Key` only and is blind to value
  types). **I checked before writing it and I was wrong**: `TestPassthroughReadDropsUnsafeRemoteURL`
  drives the real store end-to-end and asserts `len(GetRemoteData().GetFields()) != 0`, which goes
  red if the carrier type changes.

**Soundness result worth keeping:** `structpb`'s only representable *containers* are
`map[string]any` and `[]any` (enumerated from `protobuf@v1.36.11` source, not memory), and
`sanitizeRemoteValue` walks exactly those. So either the sanitizer visited every node, or the
unwalked type makes `NewStruct` fail and the field is nil. Fail-closed with no third branch —
**but only where structpb is downstream.** `export_import.go` sanitizes into JSON and has no such
backstop.

## §10.25 (added after the 05:15Z standing-rules message)

**Applying it to my own work found a hole in my headline claim.** "urlvalidate.go is comment-only"
originally rested on a filter that returned **empty** and that I had **never proved could return
anything** — an unproven zero (§10.20). Repaired with a control that could have failed: the same
filter over `convert.go` returns **13** lines, over `urlvalidate.go` **0**, and the zero is
non-vacuous because the raw diff has 24 content lines of which the filter classified all 24 as
comments, with **zero** `/* */` forms (the one shape my filter is blind to). Claim survives, having
finally been given the check it was missing.

**As a reading criterion on the round's C-1 pin:**
`TestPassthroughGraphQLRemoteDataIsNilByStructpbAccident` asserts everything against **one-key
maps** while the real `issueBuildRemoteData` output has ~13. For the *negative* assertions this is
harmless — `NewStruct` failure is monotone under adding keys, so a one-key failure cannot be
rescued. For the *positive* side it is a genuine clean plant: `parent` is pinned as a non-carrier
with a hardcoded `"node_id": "MDU6SXNzdWU="` **string**, but `githubv4.ID` is `graphql.ID` which is
declared **`ID any`** (measured in the module cache). The test plants the *assumed* dynamic type
instead of measuring the decoder's. If the decoder ever yields `json.Number` there is a third
unenumerated carrier; if it yields `json.RawMessage` the value is representable and gets silently
base64-encoded onto the wire. Not demonstrable without a build — declared, not claimed.

**Declared §10.25 gaps:** F4's and F6's absence claims have **no positive control**. I ran no
plants, mutants or exploit strings at all, so points 1–3 had nothing to apply to — where I say a
guard holds, it is from source and the round's own fixtures, not from a payload I surrounded.
